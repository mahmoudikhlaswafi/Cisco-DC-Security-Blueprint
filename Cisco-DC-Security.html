Zero Trust inside the data center

Eight Cisco products, one zero-trust design. Six of them enforce access policy at five layers: the firewall, the ACI fabric, the DPU inside a Smart Switch, the host's own firewall, programmed by Secure Workload or built into Secure Endpoint, and the Linux kernel itself, through eBPF. Security Cloud Control manages the firewall and workload policy, and Splunk observes and detects across all of them and can trigger the response.

Six products, five layers where policy is enforced

Take one intent, “Web may reach App on tcp/8443, nothing else”, and you can enforce it at five different layers. Three are in the network: the firewall, the fabric and the switch. Each layer sees different traffic, understands different identities and inspects to a different depth. To combine the products well, you first need to know where each one enforces.

Isovalent: why eBPF beats a classic host firewall

Classic host firewalls, such as the iptables or nftables rules that Secure Workload programs on Linux, live in the kernel's netfilter layer and match addresses and ports. Isovalent goes further: Cilium and Tetragon load eBPF programs into the Linux kernel, so policy runs where packets and system calls happen, keyed on workload identity, with less work per packet and per change.

Honest fine print
  • The full eBPF datapath is opt-in: with Helm defaults, kubeProxyReplacement=false and iptables masquerading stay on. Enable the kube-proxy replacement and eBPF masquerading to take iptables out of the data path.
  • L7 and DNS rules are enforced by a per-node proxy, and “L7 proxy redirection currently uses TPROXY iptables actions”.
  • Cilium needs Linux kernel 5.10 or later (4.18 on RHEL 8.10). Tetragon needs BTF. Mutual authentication is still beta.
  • Secure Workload or Isovalent? Both enforce at the workload. Secure Workload covers the broadest OS estate (Linux, Windows, AIX, Solaris) through native host firewalls, with AI policy discovery; its agent has also used eBPF for telemetry since 3.10. Isovalent is eBPF-native for Linux and Kubernetes. No integration between the two is documented, so choose per platform. For Windows and macOS there is a third option, the Host Firewall in Secure Endpoint: see the Endpoint spotlight.

Spotlight

Secure Endpoint: a host firewall inside the EDR agent

Secure Endpoint's Host Firewall lets the connector that already runs EDR on a Windows or macOS host enforce allow and block rules on that host. That covers all three focus points, but only on the hosts it runs on. It is not a second Secure Workload: rules are written by hand against IP addresses, per group of computers, and Linux gets no Host Firewall at all.

01 · East-West

Per-tier allow-lists on each host

Give each tier's policy a configuration with a Block default, then allow only the peers it needs, for example In · TCP 1433 · from App's IP on DB. Both ends can enforce, and an application path can limit a rule to one executable.

Falls shortPeers are IPs, ranges or CIDRs, so scaling a tier out means editing rules. No dependency mapping or policy discovery, and no IPS on allowed ports.
02 · North-South

Inbound and outbound rules, plus Talos reputation

Allow the Internet only to Web on tcp/443, block outbound by default, and turn on Device Flow Correlation: in Block mode it “prevents network connections to malicious hosts and reports them”, using the Talos-fed Cisco Intelligence Feed.

Falls shortNo TLS decryption, IPS, URL or FQDN rules: vendor sites must be allowed by IP. On Linux, Device Flow Correlation can only audit. Keep FTD at the edge.
03 · Microsegmentation

Same VLAN, same hypervisor: the host still decides

Rules run on each host, so two VMs in one subnet are separated without steering traffic anywhere. Endpoint Isolation is the emergency segment of one: it “blocks all network traffic except for communication to the Cisco cloud” and your isolation allow list, on Windows, macOS and Linux.

Falls shortLinux servers, Kubernetes pods and appliances get no Host Firewall, so they need Secure Workload, Isovalent or a network enforcement point.

How each product does it

Cisco ACIGA

Contracts between EPGs/ESGs, enforced in every leaf

ACI is an allow-list fabric: “Without a contract between EPGs, no unicast communication is possible between those EPGs.” A contract (subjects → filters) between a consumer group and a provider group is compiled into zoning rules keyed on the groups' class IDs (pcTags) and programmed into leaf TCAM.

  • Where: on the ingress leaf when the destination endpoint is already learned, otherwise on the egress leaf. A “policy applied” bit stops the second leaf from checking again.
  • Groups, not IPs: EPGs, attribute-based uSeg EPGs, or Endpoint Security Groups (APIC 5.0+) that can span bridge domains within a VRF.
  • Shortcuts: vzAny (every group in a VRF), preferred groups, and deny actions with four priority levels (3.2+).
Under the hood
  • Scope can be Application, VRF (default), Tenant or Global. Inter-VRF contracts are enforced in the consumer VRF.
  • Apply Both Directions and Reverse Filter Ports (both defaults) program the return rule. The filter's Stateful flag only allows provider-to-consumer TCP when ACK is set: “it does not prevent an SYN + ACK attack from the provider, unlike a stateful firewall.”
  • Rule priority: more specific EPG pairs win over vzAny and preferred groups, and within the same priority deny wins over redirect or permit.
  • Scale is roughly consumer EPGs × provider EPGs × filters. Policy-CAM size depends on the leaf model and forwarding profile; the “High Policy” profile provides 256K entries on specific -FX/-GX leaves. Bidirectional rule compression needs -EX leaves or later, and policy table compression needs -FX or later.
Secure FirewallGA

Deep inspection wherever traffic crosses the firewall

FTD enforces East-West policy on traffic that crosses it: when it is the gateway between segments or VRFs, or when the fabric redirects selected flows to it. Rules combine zones, network and dynamic objects, applications and users, and each rule can carry an intrusion and a file policy.

  • Before the rules: “Security Intelligence filtering, decryption, user identification, and some decoding and preprocessing occur before access control rules evaluate network traffic.”
  • After the allow: file and malware inspection, then Snort 3 intrusion inspection (“file inspection occurs before intrusion inspection”).
  • Rules that follow workloads: dynamic objects are filled by the FMC API, the built-in APIC connector (EPGs/ESGs) or CSDAC (e.g. vCenter attributes) without a policy redeploy.
Under the hood
  • Trust is not fastpath: traffic matching a Trust rule can still be decrypted and inspected first. To skip inspection entirely, use a prefilter Fastpath rule.
  • By default, the system does not run intrusion or file inspection on encrypted payloads.
  • Rule edits “do not apply to established connections at deploy-time”. Plan the change window accordingly.
  • To scale out, put several firewall nodes behind ACI symmetric PBR. Without resilient hashing, a node failure rehashes flows and can reset stateful connections.
HypershieldGA 10.0

Stateful L4 segmentation inside the switch

In an N9300 Smart Switch, the Silicon One NPU forwards traffic and a DPU enforces policy. Traffic in VRFs listed under the NX-OS service firewall configuration “is evaluated by the DPU against the locally installed policy before continuing through the forwarding path.”

  • Top-of-rack placement: each rack gets its own enforcement point, so capacity grows with the fabric. Cisco recommends it for “east-west segmentation close to the workload”.
  • Services placement: a shared Smart Switch pair at “inter-zone, inter-tier, or trust-boundary crossings”. The network must steer traffic to it.
  • Two designs: zone-based (broad boundaries, scales well) and workload-centric (app-to-app precision). They can be combined.
Under the hood
  • Policy lifecycle: define → review (draft in Timescape) → validate → deploy → enforce. Enforcement continues if the controller is unreachable.
  • Policies are Kubernetes resources (SmartSwitchNetworkPolicy, NetworkObjectGroup) changed only through Timescape or its REST API.
  • A change that would block a live session interrupts it after a 60-second timer. BUM traffic bypasses the DPU. HA failover can take up to 10 s, and vMotion resets sessions that cross DPU inspection.
  • Keep the management VRF out of DPU steering. Otherwise the DPU's default-deny can lock out the controller, and recovery needs console access.
Secure WorkloadGA 4.0

A miniature firewall around each workload

Secure Workload learns application dependencies from agent telemetry, proposes consumer/provider policies and pushes them to each workload's own firewall. The policy does not depend on subnets, VLANs or fabric type: “Microsegmentation creates a miniature firewall around each workload.”

  • Both ends enforce: “For traffic to pass between each consumer-provider pair, both must have a policy that allows the traffic.”
  • Policy order: absolute policies override lower ones, then default policies, then a catch-all. Set the catch-all to Allow while monitoring and switch it to Deny when ready.
  • Test before you enforce: live policy analysis and experiments against past traffic. Escaped flows are flows the network allowed but the policy would drop.
Under the hood
  • On Linux, agents use nftables from release 4.0 (with nftables 1.0.0 or newer) and otherwise iptables/ipset. Windows uses Windows Advanced Firewall or WFP, and AIX uses IPFilter.
  • Enforcement is off by default. You must enable it on both the workspace and the agent profile.
  • Enforcing deletes existing host firewall rules unless Preserve Rules is set. Preserve Rules is not supported in WFP mode and is required on Kubernetes.
  • If someone edits the rules, the agent re-applies its cached policy. Uninstalling the agent clears the policy and opens the host firewall.
Secure EndpointGA · Windows & macOS

Host Firewall rules in the EDR connector

Secure Endpoint's Host Firewall lets you “monitor, control, and secure IPv4 and IPv6 network traffic” on each Windows or macOS host. You build a configuration (default Allow or Block, then ordered rules) and assign it in the policy of a group of computers, for example one configuration per tier.

  • Rules: direction (In, Out or Any), TCP or UDP, local and remote IPs, ranges or CIDRs, ports, and optionally an application path. The first matching rule wins.
  • Both ends: give Web an Out rule and DB an In rule, and the flow is checked on both hosts, as with Secure Workload, but per group of computers and by IP address.
  • Test first: Audit mode “will not take any action on the traffic but it will create log entries”; then switch the rule to Enforce.
Under the hood
  • Up to 500 rules per configuration and 50 addresses, ranges or CIDRs per rule. Edited rules are applied as soon as you save them.
  • Connector versions: Windows 8.4.2+ (x64) or 8.4.4+ (ARM), Mac 1.24.2+. The Linux connector has no Host Firewall.
  • It works next to Windows Firewall rather than replacing it: “If either firewall has a block rule in place it will be enforced.”
  • Logs are kept on each host in FirewallLog.csv (rotated at 25 MB) and retrieved through Orbital or a diagnostics bundle. There is no dependency map or policy discovery.
IsovalentGA

Identity-based L3–L7 policy in the kernel of every node

Cilium attaches eBPF programs to each workload's network path. A policy selects workloads by label (app=web), and from then on the endpoint is default-deny: “When an endpoint is selected by a network policy, it transitions to a default-deny state.”

  • Identity, not IP: the source identity travels with the packet and is checked at the receiving node, so scaling pods out never rewrites rules on other hosts.
  • L7-aware: allow only GET /api/.* from Web to App, or specific gRPC calls and Kafka topics.
  • Process-aware: Tetragon records which binary opened each connection and can kill a process in the kernel when a TracingPolicy matches.
Under the hood
  • Policies are CiliumNetworkPolicy (namespaced) or CiliumClusterwideNetworkPolicy (cluster-wide, can select nodes). An explicit egressDeny rule wins over allows.
  • Across clusters, Cluster Mesh enforces “based on identity, not IP address, across all clusters”. WireGuard or IPsec can encrypt pod traffic transparently.
  • Hubble shows every flow with identities and the verdict, answering “Which services had connections blocked due to network policy?”
  • Until a policy selects an endpoint, it is unrestricted. The enforcement mode (default, always, never) changes that behaviour cluster-wide.

Cisco ACIGA

Steer same-subnet traffic to the leaf, then classify it

uSeg EPGs and ESGs can place hosts from one subnet in different security groups, but a leaf can only enforce traffic it receives. ACI combines PVLAN on the virtual switch with proxy-ARP on the leaf, so same-subnet traffic is routed through the leaf.

  • uSeg EPG attributes: IP, MAC, VM name, guest OS, VM tag, hypervisor and more for VMware; IP or MAC for bare metal. A uSeg EPG must belong to the same bridge domain as its base EPG.
  • VMware VDS: “Allow Micro-Segmentation” configures a PVLAN on the base EPG's port group and enables proxy-ARP.
  • Isolation building blocks: intra-EPG isolation (1.2(2g)), intra-EPG contracts (3.0), redirect/copy actions in intra-EPG contracts (4.0), and intra-ESG isolation.
Under the hood
  • With proxy-ARP, “all traffic… [is] handled as routed traffic on ACI switches, even if the source and destination IP addresses are in the same subnet”. This matters because IP-based selectors only apply to routed traffic.
  • On a VDS with isolation enforced, “all intra-ESXi host… VM traffic is sent to the Cisco ACI leaf switch”.
  • In physical domains, proxy-ARP is not always enabled. MAC-based uSeg EPGs apply to bridged traffic and IP-based ones to IP traffic, and the uSeg EPGs need static leaf bindings.
  • Intermediate switches such as UCS fabric interconnects must also carry the PVLANs, otherwise they switch the traffic locally. Proxy-ARP drops non-ARP flooded traffic and Layer 2 multicast.
Secure WorkloadGA

Same subnet, no problem: the host enforces

Host rules are written per workload IP: “firewall rules allow traffic destined to 1.1.1.2 specifically, not to the whole subnet 1.1.1.0/24.” Two VMs on the same port group are filtered by their own firewalls, with no network device in the path.

  • Covers VM-to-VM traffic inside one hypervisor, bare-metal servers and Kubernetes pods (agent or native NetworkPolicy).
  • “When a workspace is enforced, each workload receives only the policies that are specific to that workload.”
  • Moving a VM to another host or VLAN does not change its policy.
Watch-outEach workload needs an agent. Appliances and unsupported operating systems need an enforcement point in the network.
Secure EndpointGA · Windows & macOS

The Host Firewall runs in each Windows or macOS host, so two VMs on one port group are separated by their own rules, wherever the frame is switched. A Block default plus a few allow rules per role gives each host its own perimeter.

  • Rules name IP addresses, ranges or CIDRs, so a neighbour in the same subnet is just another address to allow or block.
  • Endpoint Isolation blocks a host's “incoming and outgoing network activity”, except the Cisco cloud and an IP isolation allow list of up to 200 IPv4 addresses. It also runs on Linux (1.27.0+, kernel with BTF).
  • Moving a VM to another host or VLAN doesn't change its rules, but a new IP address means updating the rules on its peers.
Watch-outNo Host Firewall on Linux, so Linux servers, Kubernetes pods and appliances need another enforcement point. Policies apply per group of computers, not per workload label.
HypershieldGA 10.0

VLAN steering: bridged traffic through the DPU

“Steering a VRF captures inter-VLAN routed traffic within that VRF but does not capture bridged traffic that stays within a single VLAN.” Steer the VLAN as well, and VLAN-scoped rules then provide “intra-VLAN lateral movement control within a single broadcast domain.”

  • Steering entries: vrf <name> module-affinity dynamic for routed traffic and vlan id <range> bridged-traffic module-affinity dynamic for bridged traffic.
  • Routed and bridged traffic from the same host are each evaluated in the right context, so “inter-VLAN segmentation and intra-VLAN micro-segmentation” can run on the same switch.
  • VLAN-object rules are enforced only when source and destination VLANs match. Use VRF objects for inter-VLAN traffic.
Watch-outThe DPU only sees frames that cross the Smart Switch. VM-to-VM traffic switched inside a hypervisor never reaches it.
Secure FirewallPossible, with redesign

Transparent mode: a bump in the wire

On its own, a firewall never sees two hosts talking inside one VLAN. In transparent mode, FTD bridges interfaces that share a subnet, so you can split a VLAN into segments and inspect traffic between them.

  • “Each directly-connected network must be on the same subnet.” With more than two interfaces in a bridge group, “you can control communication between multiple segments on the same network.”
  • ARP passes through the bridge group without an access rule. Everything else goes through access control, IPS and file policy.
  • Inline sets are IPS-only and “unrelated to the transparent firewall mode”. VLAN tags in access rules apply only to inline sets.
Watch-outYou have to re-VLAN or re-cable the segment. Bridge groups are not supported with clustering or on FTDv in public clouds, and changing the firewall mode erases the configuration. With ACI, redirect is the cleaner option (see Better together).

Design playbook

Six common starting points. Each one layers the products by what they do best: macro in the fabric, micro on the host, kernel-level policy with eBPF, endpoint detection and isolation, deep inspection at the firewall, unified management, and detection and response across all of them.

Firewall · deepService graph + PBR to FTD for crown-jewel tiers and the L3Out; FMC rules written against APIC dynamic objects
Host · microSecure Workload: discover first, then either enforce on hosts (defense in depth) or push ESGs to ACI (agentless) – one policy owner per VRF

  • Start Secure Workload in visibility mode to learn the real dependencies.
  • Use ESGs (APIC 5.0+) so security groups don't depend on bridge domains.
  • Redirect only the contract subjects that need L7 inspection.
  • Check leaf TCAM before you push generated policy. Secure Workload checks it too.
  • Send FTD events and ACI anomalies to Splunk from day one, so you have a baseline before you tighten policy.

  • Making FTD the gateway for every subnet, which hair-pins all internal traffic.
  • Treating the “Stateful” filter flag as a firewall. It only checks the ACK flag.
